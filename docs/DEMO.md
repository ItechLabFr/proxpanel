# ProxPanel Demo

The demo Docker image and deployment are intentionally independent from the normal ProxPanel release workflow.

## Image

```text
itechlab/proxpanel:demo
```

Every manual demo publication also creates an immutable image tag:

```text
itechlab/proxpanel:demo-<commit-sha>
```

## Behaviour

The **Update Demo** workflow is triggered only with `workflow_dispatch`.

A normal push, GitHub Release, Docker Hub beta/stable publication or OTA publication does not publish or deploy the demo image.

The workflow:

1. checks out the selected branch, tag or commit;
2. validates the JavaScript source and version metadata;
3. builds amd64 and arm64 images on a GitHub-hosted runner;
4. publishes `itechlab/proxpanel:demo`;
5. optionally sends the deployment job to a self-hosted runner installed on the demo server;
6. the demo server pulls the image locally and replaces only `proxpanel-demo`.

No inbound SSH or public administration port is required for deployment.

It does not create or modify a GitHub Release, publish OTA metadata, change `beta`, `stable` or `latest`, or revoke releases.

## Required Docker Hub secrets

The build job reuses:

- `DOCKERHUB_USERNAME`
- `DOCKERHUB_TOKEN`

No SSH secret is required.

## Install the self-hosted runner on the demo server

Use a dedicated non-root Linux account for the runner.

In the GitHub repository, open:

```text
Settings > Actions > Runners > New self-hosted runner
```

Select Linux and the architecture of the demo host, then run the commands generated by GitHub on the demo server.

When configuring the runner, add the custom label:

```text
proxpanel-demo
```

The workflow targets:

```text
[self-hosted, linux, proxpanel-demo]
```

Configure the runner as a service so it reconnects after a reboot. Use the service installation commands shown by GitHub for the downloaded runner version.

The runner account needs access to Docker. For a standard Docker installation:

```bash
sudo usermod -aG docker <runner-user>
```

Log out and back in (or restart the runner service) after changing group membership.

Verify:

```bash
docker version
docker compose version
```

The runner only needs outbound network access to GitHub and Docker Hub. No inbound SSH port is needed for this deployment flow.

## First demo deployment

You do not need to manually copy the compose file. During a deployment the runner copies the repository version to:

```text
$HOME/proxpanel-demo/docker-compose.demo.yml
```

The container exposes port `8080` by default.

To use another port, create `$HOME/proxpanel-demo/.env` on the demo server:

```text
PROXPANEL_DEMO_PORT=8081
```

## Updating the demo

1. Open **Actions** in the ProxPanel GitHub repository.
2. Select **Update Demo**.
3. Click **Run workflow**.
4. Keep `source_ref=main` for the latest development code, or specify another branch/tag/commit.
5. Keep `deploy_server=true` to update the demo host.
6. Use `no_cache=true` only for a full rebuild.
7. Run the workflow.

Nothing happens to the demo between manual runs.

## Manual fallback on the server

```bash
cd "$HOME/proxpanel-demo"
docker compose -f docker-compose.demo.yml pull proxpanel-demo
docker compose -f docker-compose.demo.yml up -d --remove-orphans proxpanel-demo
```

## Verification

```bash
docker compose -f "$HOME/proxpanel-demo/docker-compose.demo.yml" ps
docker logs --tail 100 proxpanel-demo
```

## Security

The self-hosted runner should use a dedicated account and should not contain unrelated credentials or production secrets.

The demo should not connect to a production Proxmox environment with privileged credentials. Use an isolated lab/demo environment and a dedicated Proxmox account with only the permissions required for the demonstration.
